# 文件编码原型：逐字节验证与撤回结果

2026-09-27。两版复用 JDK 编码器的原型均未满足提前记录的保留条件，**已撤回生产代码**。
正式传输实现仍与 `6c77ab5` 相同。本轮保留 Unicode 边界测试和更严格的基准输出对比。
全场景至少 +25%、继续争取 +50%，以及亿级无重复、无遗漏、无改值目标仍未达成。

## 定位和试验

对当前正式运行包做一次真实 PG→文件百万行 JFR 诊断。源表静态，六列；
输出 315,659,578 字节，与同顺序原生 PG COPY 结果逐块比较完全一致，随后删除数据文件。
诊断耗时 3.121 秒，含采样开销，不作为提速对照。

JFR 的 Java/native 采样间隔为 1 ms，记录上限 64 MiB，实际约 540 KiB。
454 条 Java 执行采样中，writer 线程 275 条、reader 144 条；UTF-8 Encoder 为 92 条叶节点。
导出的最多五层调用栈中，127 条含 flushRecords。它们是采样计数，不能相加成墙钟耗时占比。
原始 JFR 留在本地；公开选定事件、方法统计、运行配置和结果，不发布环境变量等初始化事件。

第一版用 OutputStreamWriter 和复用的 64 KiB 字符缓冲，替代每批 String/byte[] 复制。
编码器的全部写入和 flush 都在原有整行输出锁内；异常时只关闭原始文件流，避免关闭包装层时
再次 flush 失败批次。第二版增加固定 64 KiB BufferedOutputStream，以测试合并小写入的效果。
没有新增依赖、改分片数或改变源查询。

第一版混合字段组的用户 CPU 中位数均为 2.39 秒，系统 CPU 从 0.31 升到 0.42 秒。
这促成第二版缓冲试验，但没有据此断言已证明所有时间变化的原因。

## 完整对照

每版、每场景各一次预热，再五对 AB/BA。对照分别是前版 fork `6c77ab5` 和未修改上游
`80ec23d`；两种场景为六列混合数据、八列整数边界/NULL 数据。每次一百万行，完整 JVM 计时，
排除原生参考输出、事后验证和建表；计时期间没有其他本地构建、采样或功能测试。

两版都以“两个场景相对前版中位吞吐各提高至少 5%，并通过全部数据检查”为保留条件。
这仅是是否保留局部改动的条件，不替代全场景 +25% / +50% 的验收门槛。

| 原型 | 对照 | 混合六列吞吐变化 | 整数八列吞吐变化 |
|---|---|---:|---:|
| 复用编码器 | 前版 fork | −9.63% | +0.28% |
| 复用编码器 | 未修改上游 | +17.13% | +9.83% |
| 编码器 + 固定缓冲 | 前版 fork | −1.22% | −9.77% |
| 编码器 + 固定缓冲 | 未修改上游 | +20.56% | +30.93% |

八组共 96 次百万行输出，均逐字节匹配相应原生参考；没有跳过预热的数据检查。
所有组的逐轮 +25% / +50% 门槛均失败。最后一项虽然中位超过 25%，最差配对仅 +7.17%，
且相对前版的独立对照退化，不计作达标。不同组的基线耗时也有明显波动，不能跨组拼接收益。

Apple M5 / 16 GiB；PG 17.11，4 CPU / 2 GiB，三项持久化设置均开启。
双方 JDK 8u504、1 GiB JVM、UTC、单通道、fetchSize=1024。既有其他项目容器继续运行；
这些是本机配对结果，不代表独占机器或生产环境。原始耗时、CPU/RSS、全部配对和配置均保留。

## 验证和最终保留内容

- 两个原型分别通过 24 项完整 Engine 文件检查，覆盖多字符分隔符、Unicode、并发和宽行。
- 原型分别通过 61 项 JUnit；撤回生产代码后的最终 61 项也通过。不是 183 项独立用例。
- 保留一项 Unicode 边界检查，覆盖 8 KiB / 64 KiB 附近的合法代理对；原型另比较过旧编码器
  对非法 UTF-16 的替换行为，该兼容性探针不作为无损传输标准，源码仅在试验归档中保留。
- `postgresql_scenarios.py` 在原有行数/内容指纹之外，保留有序原生参考文件，用标准库
  `filecmp.cmp(..., shallow=False)` 每轮逐字节核对；比较前清除缓存，输出与参考及时删除。
- 恢复后的生产 class 与正式运行包逐个相同，没有把任一编码原型加入正式执行路径。

文件格式的 NULL/文本歧义、分隔符/换行、非法 UTF-16 等仍不具备任意数据无损语义；
上述检查只证明指定夹具输出一致。也没有整作业原子发布、亿级容量或生产错误率证明。

## 复现、证据与空间

按[构建指南](README.md)准备运行包，复用专用 PG 的百万行源表：

```sh
python3 benchmarks/postgresql_scenarios.py /tmp/datax-before /tmp/datax-candidate /tmp/file-mixed --scenario pg-to-file --rounds 5
python3 benchmarks/postgresql_scenarios.py /tmp/datax-before /tmp/datax-candidate /tmp/file-integer --scenario pg-integer-file --rounds 5
```

原型基于 `f20bbf0` 加各自归档补丁构建；完整补丁哈希与运行包的 tracked_diff_sha256 一致。
不能把原型运行包称为正式发布版本。保留计划在各次计时前保存；第二版计划也记录其动机及停止条件。
初次开发编译的同名 Writer 类型冲突日志同样保留，修正后才运行功能与性能检查。

没有新建数据库或容器。每组同时保留参考和当前输出，逐轮删除输出、组末删除参考，
轮次间按现有 6 GiB 数据预算检查并预留 1 GiB；它不是全过程硬配额。
两个试验运行包在归档与 JAR 哈希核验后删除，释放约 281 MiB。
临时根目录约 886 MiB，既有 PG 数据目录约 1.37 GiB，本轮证据约 1.8 MiB。
