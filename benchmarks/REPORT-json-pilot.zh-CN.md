# JSON 编码原型：当前运行包采样与独立对照

2026-09-27。正式运行包仍为 `305cd33`（发布说明提交 `487dd82`）。本轮在相同配置下评估一个减少逐行 HashMap 分配的原型；**全场景 +25% / +50% 和亿级零差错目标仍未证明。**

## 从当前运行包采样

对当前版本的真实 PG→StarRocks 单路百万行 JSON 传输采集 JDK 8 JFR，Java/native sampling 均为 1 ms；记录上限 64 MiB。作业结束后核对行数、去重键数及全部六列，均为预期值。剖析本身有开销，9.116 秒只作为诊断记录，不混入性能对照。

987 个 Java 执行样本中，writer 648、reader 240；JSONWriterUTF8.writeString 是 206 个样本的叶节点，HashMap.putVal 为 23。DateCast.asString 出现在 168 个执行样本的栈中。另有大量 native socketRead 样本，异步 Stream Load 工作线程主要在接收数据库响应。这些是采样与栈覆盖计数，不是各功能可直接相加的墙钟耗时百分比。

原型复用已有 Fastjson JSONWriter：预先计算字段的 HashMap 遍历顺序，每行先按原配置顺序转换字段，再输出相同 JSON 字节，避免每行建立节点表。重复/NULL 字段名、构造后字段列表变化及全局 JSON 特性继续走原有 Map 路径。仅涉及 SR/Doris JSON 字节编码，没有改变读取、分片、提交、重试、批次阈值或 CSV 路径，没有新增依赖。

## 功能检查与测量方法

原型完整单元测试 57 项通过，新增两项多字段对照覆盖 Unicode、NULL、unsigned bigint 文本、精确小数、显式二进制编码、重复/NULL 字段名、128 个哈希冲突字段及字段列表修改。它们是编码检查，不能称为真实服务端或亿级恢复验证。

四组计划在计时前固定：SR 和 Doris 的 writer-json，分别对照前版 fork 与未修改原版 `80ec23d`。每版各预热一次，再执行五对 AB/BA；每次百万行均核对总数、精确 COUNT(DISTINCT id) 和全部字段，不用目标唯一键隐藏重复。JVM 生命周期计时，排除建表、清空、检查及采样开销；不在计时期间构建或运行其他本地基准。

PG 使用既有静态百万行六列源表，17.11、4 CPU / 2 GiB，持久化三项均开启。各 OLAP 容器总限制 4 CPU / 4 GiB；Doris 的 BE 额度变化见下文。StarRocks 4.1.4、Doris 4.1.3-rc02，同一固定镜像对照。双方 JDK 8u504、1 GiB JVM、UTC、fetchSize=1024、单通道、5 MiB 字节批次、500000 行上限、队列长度 1，strict_mode=true、max_filter_ratio=0。

本轮修正 `olap_scenarios.py` 对 Doris 的批次参数名为 `batchSize`；SR 仍用 `maxBatchSize`。历史 OLAP 报告已注明旧脚本的 Doris 实际默认 90 MiB，本轮不修改历史原始数据，也不把新旧组拼接计算收益。

## 完整记录和结论

按预先记录的保留条件，两种 JSON writer 相对前版都要有中位吞吐改善且通过数据检查。Doris 相对前版中位下降 3.44%，条件未成立；已撤回两份生产 JSON 编码原型，正式实现保持原样。新增多字段字节兼容性测试保留，未将原型合入默认执行路径。

基准工具保留两个修正：Doris 使用真实生效的 batchSize；每次作业运行/校验前持久化 pending_run，校验完成才移入完成列表。性能门槛明确拒绝带未完成校验的记录，避免发生这次“Engine 返回成功但外部对账失败”时只留下之前的成功样本。该验证器检查另有纯合成自测，不计作真实性能测量。

原型来自 `487dd82` 加归档补丁，运行包元数据的 tracked_diff_sha256 与补丁文件哈希一致；不是干净发布构建。记录源码补丁、测试日志、每次配置/日志、JAR 哈希与采样汇总，不将这个试验包冒充已发布的正式版本。

第一组 SR→前版对照完成后，最初接续运行的 SR→上游对照因累计存储达到 5,481,373,696 字节、再加预留 1 GiB 将超出 6 GiB 预算而停止。已完成轮次和原始异常保留，该组标为不完整；随后删除专用 SR 容器，在新容器完整重跑五对，没有删除慢轮来改善数字。后续每组新建、组末删除容器。存储限制是轮次间检查，不是文件系统硬配额。

Doris 默认 BE 配额为容器的 40%（1.6 GiB）。第一次对前版比较完成 6 次校验，第 7 次 Engine 已成功结束，但 COUNT(DISTINCT id) 和字段核对查询因 BE 进程约 1.59 GiB、申请额外 9 MiB 触发 MEM_LIMIT_EXCEEDED 而失败。该次字段状态未核实，不能计作成功校验；已保存 DataX 日志、查询错误和容器状态，容器并未被系统 OOM kill。

随后新增两组明确标识的 BE 2.4 GiB 对照：容器总限制仍为 4 GiB，通过 BE_CONFIG_EXTRA=mem_limit=60% 给双方相同额度，在新容器分别重跑五对。这些新控制组不覆盖原 1.6 GiB 组失败的事实。

收尾已删除全部本轮 SR/Doris 容器及试验运行包（147,383,881 字节）；保留正式运行包和未修改原版。临时根目录约 831 MiB，PG 数据目录约 1.37 GiB，没有新建大源表。采样最高数据库占用约 5.10 GiB；这不是全过程硬上限或亿级容量证明。
