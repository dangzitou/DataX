# 非 querySql 场景补测与数据描述勘误

2026-09-26。原版 `80ec23d` 与已发布优化版的干净运行包 `6c93d16` 比较；生产代码没有继续改动。本轮补充原先缺少的普通表、文件输出和写入侧证据。

**四组均未达到逐轮提升 50%。** 普通表单路提升 9.49%，普通表四路提升 4.78%，文件输出约 0%（0.05% 差异不足以认定有效收益），生成数据写入 MySQL 提升 7.83%。不能把 querySql 的自动并行收益推广到这些场景。

|---|---:|---:|---:|---|
| 普通表 → MySQL，单路 | 13.115s | 11.978s | +9.49% | 未通过 |
| 普通表 → MySQL，四路 / 原有 splitPk | 8.720s | 8.322s | +4.78% | 未通过 |

| 生成常量记录 → MySQL，四路 | 8.376s | 7.768s | +7.83% | 未通过 |

每组每版各预热一次，再测五对 AB/BA 交替运行；共 48 次成功的百万行传输，检查均通过。吞吐变化仍按两版耗时中位数的比值计算，完整 JVM 启动、初始化和读写都包含在内。建表、事后验证、参考文件导出不计时。所有轮次保留；有限样本、共享主机和启动开销都限制了结论，不构成未来运行的性能下限。

## 四组分别证明了什么

- **普通表单路**：使用 `table`/`column` 配置，两版均一个任务，不包含 querySql 自动分片收益。目标有主键，每轮核对总数及六列的 NULL 安全相等。
- **普通表四路**：两版都使用原有 `splitPk=id` 和默认 splitFactor，日志确认各拆成 21 个任务（包括 NULL 分片），并发均为 4；逐字段核对目标表。
- **MySQL → 文件**：使用已有 `streamwriter` 的文件输出模式，一个任务；每轮实际写入 318,952,336 字节 UTF-8 TSV，与直接 MySQL 导出的完整 SHA-256、字节数和百万行数相同。没有测试 txtfilewriter、HDFS 或 OSS。遵循插件原有 flush 行为，不包含额外 fsync，不能当成持久化磁盘带宽测试。此固定源表实际按主键扫描，顺序也参与字节比对，不表示任意任务都有排序保证。
- **生成数据 → MySQL**：StreamReader 生成相同常量记录，四路各 25 万行；目标无主键，检查总数和全部字段，包括真正中文。该场景用于观察写入侧成本，不模拟外部读取、不同业务行或实际生产数据分布。

硬件、JDK、MySQL、内存、batchSize、持久化设置与[此前环境](results/2026-09-26-final/environment.json)相同。两版配置一致，未增加新版并发。旧通道微测试的 55.87% 只代表该组件，不等于数据库或文件整条链路。

## 必须更正的字符集描述

本次常量写入验证发现：旧基准脚本调用 MySQL CLI 时没有显式字符集，本机容器客户端使用 `latin1`。UTF-8 造数语句的“中文”被解释为非预期字符，原表 `id=1` 的文本实际字节是 `C3A4C2B8C2ADC3A6E28093E280A12D31`，而非预期中文 UTF-8。此前报告把这些文本称为中文，描述不准确；旧 Unicode/emoji 功能用例也不足以证明预期字符的保真。

**这不会把旧记录改成另一组成绩：两版始终读取同一张表，原有耗时和表间相等验证仍是该实际样本的证据。** 前三组补测沿用同一历史样本，未中途重造数据；它们应描述为含非 ASCII 文本的生成数据。当前脚本已明确设置 `--default-character-set=utf8mb4`，今后 `--seed` 会生成正确中文，因此数据内容与历史样本有所不同。历史生成脚本可在 `f9da921` 提交中复原，原始日志、脚本历史和样本字节一并公开。

新增字符集前置检查直接验证 `HEX('中文😀')`，修复后为 `E4B8ADE69687F09F9880`。**42 项真实 MySQL 功能检查重新通过**，包含正确中文、emoji、二进制和控制字符的客户端/服务端预编译往返。

独立写入有两次被排除的预检：第一次因 StreamReader 不支持 NULL 常量在处理记录前失败；第二次 DataX 写入正确中文，但旧 CLI 的校验常量被误解导致验证失败。修复配置和客户端编码后，从预热开始完整重做五对实验。两次日志均保留，没有把失败预检混入或挑选为正式成绩。

## PostgreSQL 与生产使用边界

这些是 MySQL 场景，**尚未完成 PostgreSQL 亿级回灌验证，也不能证明改版在 PG 上错误率不增加**。新增 `querySqlSplitPk` 目前仅支持 MySQL。PG 插件会使用本次变更涉及的公共通道、读取转换和 JDBC writer，必须针对实际源/目标、字段类型和失败恢复另做验收。

当前 PG 读取没有跨任务统一快照协调；PG 的单个 SELECT 快照不等于多个并行连接共享同一快照。导入统一快照需要符合事务隔离和执行时序要求，参见 [PostgreSQL 官方事务说明](https://www.postgresql.org/docs/17/sql-set-transaction.html)。本 fork 尚未实现这种协调机制。

公共 JDBC writer 分批提交，任务失败不会回滚此前全部批次。`errorLimit.record=0` 让已检测到脏记录的任务失败，不保证目标从未写入半成品，也不能代替精度/时区等字段级校验。PG writer 当前只实现 INSERT；直接重跑需要另外解决重复、冲突和部分提交问题。不能把百万行零差异或 MySQL 性能达标当作亿级 PG 生产安全背书。

进一步按当前公共读写路径做了时间戳转换检查：`Timestamp → DateColumn → java.util.Date → Timestamp` 将 `2024-01-01 12:34:56.123456` 变为 `2024-01-01 12:34:56.123`。原版和新版各独立运行四次均复现，属于两版共有的毫秒精度限制，并非本轮优化新增。[探针和八次原始输出](results/2026-09-26-pg-audit/timestamp-precision-artifacts.json.gz)公开保留；这是 Java 转换检查，**不是 PG 数据库往返测试**。存在微秒保真要求时，该路径不能直接验收，即使任务成功、行数相同、脏记录计数为零。

亿级生产链路必须先明确最终目标库、源是否持续变化、唯一键及字段类型，再验证固定快照或静态源、分片覆盖、重跑幂等性、故障注入和逐字段对账。建议先写隔离暂存结果，只有完整对账通过后才发布；失败结果不得作为完整回灌供业务使用。此报告没有批准任何生产切换，也没有声称已解决上述 PG 边界。
