# DataX MySQL / querySql 优化与实测报告

> 历史结果：本文件保留第一轮原始结果；当前交付版本及逐轮验收见[最终报告](REPORT-final.zh-CN.md)。第一轮中位数达标，但并非每轮都达到 +50%，不能作为最终逐轮验收结果。

测试日期：2026-09-26。性能代码提交：[`456a29b`](https://github.com/dangzitou/DataX/commit/456a29b655ce5560b49c0d5d4349158c0a236dc1)。
原版基线：Alibaba DataX [`80ec23d`](https://github.com/alibaba/DataX/commit/80ec23d5c5328eb90ca364d2749e92dfaf44541e)，独立 worktree，源码未修改。

**100 万行 MySQL → DataX → MySQL 同步，五轮中位数由 14.752 秒降至 9.783 秒，吞吐提升 50.79%，耗时减少 33.68%。每轮都逐字段比对，数据差异为零。**

这个提升来自新增的单条 querySql 自动并行能力。关闭该功能时，整体吞吐基本持平；与原版手工分片相比也没有额外的 50% 提升。不能将结果理解为所有 DataX 任务、所有数据库或所有配置普遍提速 50%。

## 改了什么

| 范围 | 实际改动 | 验证 |
|---|---|---|
| MySQL querySql | 新增可选 `querySqlSplitPk`，按查询输出整数列发现 MIN/MAX 并生成互不重叠的范围任务；包含 NULL、开放边界，支持 unsigned BIGINT | 真实库全量同步、边界数据、JOIN/表达式/过滤、ORDER BY + LIMIT、UNION ALL |
| 公共内存通道 | 使用一个锁保护 ArrayDeque 与字节计数，消除批量入队中的逐条嵌套加锁；单条/批量操作统一唤醒 | FIFO、容量、清空、超大批次、中断、结束信号回归；独立吞吐测试 |
| 公共 JDBC 读取 | 每个结果集缓存字段类型；整数直接解析 BigInteger，保留科学记数法与截断兼容行为 | 元数据调用次数、数值边界、原有转换语义单测 |
| 数据正确性 | 保留 boolean、YEAR、强制编码字符串的 NULL；转换失败后不发送半条记录；JDBC 访问失败使任务失败 | 单元故障注入、真实库逐字段比对 |
| 错误与资源管理 | 先按 SQLState/vendorCode 和异常链分类，再用原有文本匹配；识别旧 MySQL 驱动的特殊超时类；补齐 statement、connection、预检查线程池的失败清理 | SQL 错误、超时、四次主动断连、资源关闭单测 |
| 预检查 | 每条 querySql 都实际验证，使用 `setMaxRows(1)`；校验新切分键和超时参数 | 第二条 SQL 缺列、缺失/错误类型切分键、合法 dryRun |

`rdbmsreader` 删除了与公共读取器重复的转换实现，从公共实现继承这些修复。其他拥有自定义读取实现的插件不能据此认为已经覆盖。

## 测试方法和环境

- Apple M5，10 个逻辑 CPU，16 GiB 内存，macOS 27 / arm64；MySQL 8.0.46 在 OrbStack Docker 中运行，限制 6 CPU / 4 GiB，InnoDB buffer pool 1 GiB。
- JDK：Zulu 8u504；MySQL Connector/J：原版相同的 5.1.47；两版 DataX 均为 `-Xms1g -Xmx1g`，channel 上限 4，writer batchSize 1024。
- 数据集：100 万行、6 列，包含整数、DECIMAL、DATETIME、中文、NULL；每行 payload 为 256 字节，58,823 行可空文本为 NULL。数据为脚本生成的测试数据。
- MySQL 的 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`，两版相同。未通过关闭持久化换取提升。
- 两版先各预热一次，然后 AB/BA 交替测量五轮。计时覆盖 JVM 启动、初始化、范围发现和完整读写，排除建表/造数及事后校验。两版 job 完成轮询间隔均设为 200ms，避免默认 10 秒轮询造成粗粒度计时。
- 每次都重建目标表；校验总行数，并用 MySQL `<=>` 对所有字段做 NULL 安全比对。目标表主键拒绝重复 ID。三组实验共 36 次完整同步（含预热），合计 3,600 万行，均完成校验。
- 通过 EXPLAIN 确认主测试的外层范围谓词使用源表 PRIMARY 的 range 访问。该结论不自动适用于其他复杂 SQL。
- 各组按顺序独立测量；本机与数据库共享硬件，没有 CPU 绑核、频率控制或随机化实验。存在运行波动，没有建立性能下限或统计置信区间。

吞吐提升 = `原版耗时 / 改进版耗时 - 1`；耗时减少 = `1 - 改进版耗时 / 原版耗时`。两者不能混用。

## 完整数据库同步结果

| 实验 | 原版实际任务数 | 改进版实际任务数 | 原版中位数 | 改进版中位数 | 吞吐变化 |
|---|---:|---:|---:|---:|---:|
| 单条 querySql → 自动并行 | 1 | 4 | 14.752s | 9.783s | **+50.79%** |
| 相同配置，均不启用新功能 | 1 | 1 | 12.863s | 12.890s | -0.21% |
| 原版手工四条 SQL → 自动并行 | 4 | 4 | 9.111s | 9.418s | -3.26% |

上述数字分别来自各组内部对照，不能将不同组的基线耗时混合计算。手工分片对照说明，主要收益是让单条 querySql 使用已有并发资源，并非让已经并行的任务再获得 50% 提升。此轮自动分片比手工分片中位数略慢，报告保留该结果。

主实验每轮数据如下；50.79% 是五轮中位数的点估计，**不是每一轮都超过 50%**。

| 轮次 | 原版秒数 | 改进版秒数 | 本轮吞吐变化 | 不一致行数 |
|---|---:|---:|---:|---:|
| 1 | 14.752 | 10.891 | +35.45% | 0 |
| 2 | 14.434 | 9.290 | +55.37% | 0 |
| 3 | 14.873 | 9.783 | +52.02% | 0 |
| 4 | 14.407 | 11.241 | +28.17% | 0 |
| 5 | 16.717 | 8.558 | +95.35% | 0 |

主实验吞吐中位数约为 **67,786 → 102,214 行/秒**。DataX 进程峰值 RSS 的中位数为 **434.86 → 475.80 MiB（+9.41%）**；并发会占用更多内存。DataX 进程 user+system CPU 秒数中位数为 6.98 → 6.96，不含 MySQL 服务端 CPU，不能据此声称整个系统 CPU 用量降低。

## 内存通道独立微基准

使用实际 MemoryChannel，容量 512，批次 32；每个 JVM 先预热 1,048,576 条，再测 67,108,864 条，交替五轮。检查接收数量及 FIFO 顺序。

原版中位数 **3.230s**，改进版 **2.072s**，吞吐约 **2,078 万 → 3,238 万条/秒，提升 55.87%**。

此测试复用 32 个记录对象，包含同步、唤醒和结束信号，**不包含记录创建、JDBC、序列化或磁盘，不能当作数据库端到端提升**。完整数据库对照仍以上表为准。

## 稳定性和错误检测证据

- 选定模块的 **23 项单元测试全部通过**。其中 20 项可直接在两版运行的回归检查，原版连续四轮都是 16 项失败，改进版连续四轮全部通过。包含行为修复和元数据缓存检查，失败数不等同于 16 个独立线上事故。
- **28 项真实 MySQL 检查全部通过**：10 项结果正确性检查，9 项错误/配置检查，5 项 dryRun 检查，以及 4 次主动 KILL 读取连接。断连后的 DataX 进程均非零退出并识别为连接故障。
- [GitHub CI](https://github.com/dangzitou/DataX/actions/runs/36235637589) 在 Linux / Temurin 8 上再次通过 23 项单元测试和 28 项真实 MySQL 检查。CI 使用 10,000 行样本验证功能，**没有在 CI 中宣称性能提升比例**。

原版的典型复现包括：清空队列后字节配额仍被占用、超过容量的批次不再前进、中断时异常被错误解锁覆盖、NULL 转成 false/空字符串、数据库访问异常被记为脏数据后继续发送不完整记录、失败 SQL/session 未关闭 statement。修复与复现脚本同仓保存。

## 使用和限制

完整构建、测试命令和配置示例见 [复现指南](README.md)。在 `mysqlreader.parameter` 中增加 `"querySqlSplitPk": "id"`，配合 channel 数开启。`queryTimeout` 单位为秒，0 禁用 JDBC statement timeout，省略则保留上游默认值；它不是整个任务的超时上限。

并行 SQL 必须使用稳定数据源和确定性查询；多个 JDBC 连接没有共享事务快照。并发修改、非确定性函数、会话变量、没有确定排序的 LIMIT 可能导致不一致；排序也不会跨任务保留。倾斜切分键、物化子查询和写端饱和可能无收益或退化。请先确认索引和执行计划。

本次验证范围是公共传输链路、公共 JDBC 读取和 MySQL 8.0。其他数据库/插件、生产规模、跨机高延迟网络、多小时稳定性及所有可选插件的完整构建均未验证。构建脚本只打包已验证的核心和相关插件，避开上游旧 assembly 配置问题，没有声称上游所有模块都能直接构建。
