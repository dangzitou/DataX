# 最终验收：querySql 自动并行与 JDBC 稳定性改进

> 后续补测发现字符集描述问题：旧 CLI 按 latin1 解释 UTF-8 造数语句，实际文本是非预期字符。此前称为中文/emoji 保真验证不准确；两版同源耗时和相等校验记录保留。修复后的 42 项检查、非 querySql 场景和 PG 使用边界见[补测报告](REPORT-scenarios.zh-CN.md)。本报告不是 PostgreSQL 亿级生产回灌验收。

2026-09-26，**100 万行 MySQL → DataX → MySQL，原版单条 querySql 与新版自动四路并行比较，七轮吞吐提升均超过 50%：最低 62.86%，按两版耗时中位数计算提升 72.66%。** 每轮完整比对行数和字段，数据差异为零。

这是固定负载下的真实数据库端到端结果。不开分片的对照为 +4.80%，原版已手工四路并行的对照为 +3.72%，**不能据此保证所有 DataX 任务或未来每次运行都提升 50%**。主实验耗时减少 42.08%，并未达到耗时减半。

## 七轮完整链路结果

| 轮次 | 原版耗时 | 新版耗时 | 吞吐提升 | 差异行数 |
|---|---:|---:|---:|---:|
| 1 | 15.072s | 7.331s | 105.59% | 0 |
| 2 | 12.957s | 7.956s | 62.86% | 0 |
| 3 | 13.502s | 7.775s | 73.65% | 0 |
| 4 | 13.183s | 8.051s | 63.74% | 0 |
| 5 | 13.794s | 7.617s | 81.09% | 0 |
| 6 | 13.389s | 7.820s | 71.23% | 0 |
| 7 | 13.614s | 8.176s | 66.50% | 0 |

中位耗时 **13.502s → 7.820s**，对应 **74,066 → 127,884 行/秒**。吞吐提升公式为 `baseline_seconds / candidate_seconds - 1`；耗时减少公式为 `1 - candidate_seconds / baseline_seconds`。各轮和中位数均使用未舍入原始耗时计算。

验收脚本要求**每一对**测量都达到 +50%，任一轮不足、丢失证据、行数或字段校验失败均非零退出。本次主实验七轮全部通过；没有删除慢轮次，也不以中位数代替逐轮验收。若门槛改为“耗时减少 50%”，则本次结果不通过。

DataX 进程峰值 RSS 中位数 **442.16 → 455.36 MiB**，增加约 2.99%；进程用户态加内核态 CPU 时间中位数 **7.06 → 5.62 秒**，减少约 20.40%。后者不包含数据库 CPU，不能推断整机成本同比下降。

## 对照与收益来源

| 场景 | 测量轮数 | 原版中位耗时 | 新版中位耗时 | 吞吐变化 | 每轮至少 +50% |
|---|---:|---:|---:|---:|---|
| 原版单条 querySql → 自动四路并行 | 7 | 13.502s | 7.820s | **+72.66%** | 通过 |
| 两版均不分片，各一条任务 | 5 | 13.335s | 12.724s | +4.80% | 未通过 |
| 原版手工四路 → 自动四路 | 5 | 9.084s | 8.758s | +3.72% | 未通过 |

主要收益是让原版单条 querySql 可以自动并行。两组对照不足以证明在已经并行的任务上还能普遍额外提升 50%；小幅差异也可能受主机波动影响。各组独立预热，不能跨组挑选不同基线计算收益。

## 实际修改

- **querySql**：MySQL reader 增加可选 `querySqlSplitPk`，对整数输出列发现范围并生成互不重叠的查询；处理 NULL、空集、单值、重复键及 signed/unsigned BIGINT 边界，保留原 SELECT 的过滤、连接、别名和表达式。多个查询共享并发预算，不使用 OFFSET。没有设置该参数时保留原任务数。
- **通道与转换**：MemoryChannel 使用单锁有界队列和条件唤醒，去掉嵌套锁及固定轮询；修复字节预算、清空后的计数、超大记录和中断处理。读取时缓存列元数据，整数走快速转换，保留科学计数法等原有兼容路径。
- **读取与错误**：保留数值/布尔 NULL，转换失败不发送半条记录；ResultSet/JDBC 读取异常使任务失败。SQLState、厂商错误码及异常链辅助区分缺表、缺列、语法、权限、连接和超时错误。`queryTimeout` 用于实际查询、分片范围发现和预检查；dry-run 检查所有 querySql，异常路径释放连接/语句。
- **写入**：减少重复 autocommit 设置，直接绑定可表示的有符号整数，保留 unsigned BIGINT 和其他输入的兼容路径。MySQL 默认使用现有驱动的服务端预编译缓存，显式 URL 配置优先；没有保留第二轮尝试的应用层语句缓存。逐批提交及失败后回滚、逐行处理的边界保持不变。
- **缓存批次正确性**：每次取得语句先清除旧 batch，避免类型转换在 executeBatch 前失败后，驱动缓存再次执行旧记录。BOOLEAN/BIT 写入显式保留 NULL，元数据失败也关闭连接。

驱动选项及恢复客户端预编译的方法见[配置说明](README.md#mysql-writer-defaults)。服务端无法预编译的语句可由现有驱动回退；已实际验证 100 列 × 1024 行超过 65,535 参数限制的宽表批次。

## 正确性和错误检测证据

**29 项 Java 单元测试、41 项真实 MySQL 检查通过，Linux / Temurin 8 的 [GitHub CI](https://github.com/dangzitou/DataX/actions/runs/36239673294) 同样通过。** CI 使用 10,000 行功能数据，不用共享 CI 机器的耗时证明性能。

其中 26 项回归用例对两版各独立运行四次：原版每次 22 项失败，新版每次零失败。它们包含新增功能验收和缺陷回归，不能将 22 项全部解释为 22 个原版缺陷。性能门禁另有合成数据自检，和真实数据库证据分开记录。

真实数据库检查包括 SQL 边界、NULL、unsigned BIGINT、过滤/连接/UNION/LIMIT、无效配置、缺表缺列、语法错误、超时、dry-run、四次主动终止读取连接、四次批次主键冲突恢复，以及以下新增检查：

| 问题/场景 | 复现与验证 |
|---|---|
| 驱动缓存残留批次 | 在此前 `417623d` 候选版显式打开驱动缓存，日期转换中途失败；无主键目标表预期 5 行却写出 6 行，四次均复现同一条重复记录。修复后四次均为 5 行且字段一致。 |
| nullable BIT | 此前候选版写 NULL 时 Boolean 拆箱抛空指针，四次复现。最终版在客户端/服务端两种模式均保持 NULL、false、true。 |
| 类型与字符 | 两种预编译模式均核对二进制 00/FF、Unicode、控制字符、引号和毫秒时间戳。 |
| 宽批次与写入模式 | 100 列宽批次回退、replace、update 均真实落库并核对结果。 |

本地前 39 项检查使用与正式构建相同 JAR 的运行包，之后补充两项 replace/update 检查；CI 在同一流程连续执行全部 41 项。主实验和两组对照包含预热共完成 **40 次百万行同步**，每次都核对行数及全部字段，零差异。

## 环境和计量方法

- Apple M5，10 逻辑 CPU，16 GiB，macOS 27；OrbStack 中 MySQL 8.0.46，容器限制 6 CPU / 4 GiB，buffer pool 1 GiB。镜像 SHA-256 为 `7dcddc01f13bab2f15cde676d44d01f61fc9f99fe7785e86196dfc07d358ae2b`。
- 两版均为 Zulu 8u504、Connector/J 5.1.47、JVM 堆 1 GiB、channel 上限 4、batchSize 1024、完成轮询 200ms。主实验原版实际一条任务，新版四条；JDBC 驱动参数默认值属于本次源码改动，脚本未为某一版单独调整 URL。
- 源表 100 万行、6 列，含主键 BIGINT、INT、DECIMAL、DATETIME、中文、58,823 个文本 NULL 和 256 字节 payload；由脚本生成，走真实 MySQL 协议和真实 DataX Engine，不是 mock 或通道微测试。
- `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`，两版均未降低持久化要求。实验期间源表静止。
- 每组每版先预热一次，不纳入统计；随后 AB/BA 交替顺序，变体顺序执行。计时覆盖 JVM 启动至成功退出，包括初始化、范围发现、读取、转换、通道及写入；排除建表/造数和事后校验。
- 每轮重建目标表，用主键约束发现重复 ID，再核对总行数及每个字段的 NULL 安全相等。日志、配置、计时、RSS 和 CPU 数据全部保存。
- 主机与数据库共享硬件，没有绑核或固定频率；有限样本不构成未来运行下限。没有验证未知生产 SQL、多小时压力、所有可选插件或其他数据库的端到端表现。

## 使用与复现

按[构建、测试及配置指南](README.md)构建此 fork。在 `mysqlreader.parameter` 增加 `"querySqlSplitPk": "id"`，并设置 `job.setting.speed.channel=4`；`id` 应替换为查询输出中的合适整数列。正式测量后运行：

```sh
python3 benchmarks/performance_gate.py /tmp/datax-benchmark/parallel/results.json \
  --metric throughput --threshold 50 --minimum-rounds 7
```

自动分片要求确定性的查询和稳定数据源；各任务不共享事务快照，也不保证跨任务排序。数据倾斜、索引、子查询物化、写入端能力和限速都会影响收益。未知业务的“至少 50%”需要使用真实业务数据、SQL 和资源限制重新跑同一门禁。
