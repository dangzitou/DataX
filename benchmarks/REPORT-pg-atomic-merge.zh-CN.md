# PG 原子发布：两项未通过性能门槛的试验

2026-09-27。本轮没有保留生产性能改动：指纹投影和 PG 17 逐行发布两个原型均撤回，完整失败记录保留。只新增 24 次可重复的正确性边界检查。**全场景最低 +25%、目标 +50% 与亿级零差错均未验收。**

## 完整作业结果与保留决定

基线均为 clean `c9b499f` 的 `candidate-atomic-group-final`；候选为 `2c94c0f` 加各自归档补丁。双方均启用同样的原子模式、相同并发，PG 源使用共享快照，JDBC rewrite/COPY 均未开启。每场景一百万行，双方各一次预热、五对 AB/BA；完整 JVM 计时包括读取、暂存、指纹、字节核对、账本及提交。建表和外部数据核对不计时。

| 原型 / 场景 | 前版中位秒 | 候选中位秒 | 中位吞吐变化 | 最差配对 | 每对 +25% / +50% |
|---|---:|---:|---:|---:|---|
| 指纹投影 / 普通表单通道 | 14.4822 | 13.9551 | +3.78% | −23.57% | 均失败 |
| 指纹投影 / 生成数据四通道 | 10.0394 | 8.5220 | +17.81% | +16.78% | 均失败 |

60 次百万行作业均通过数量、全部六列、账本及无遗留暂存检查。生成记录场景是百万行相同值，保留其重复数量，不代表百万条不同业务记录。

两项试验各自在启动前记录：所测各场景中位至少 +5%、每对不退步且正确性通过才保留；用户的每对 +25% / +50% 另行评估。两项均出现负收益配对，因此撤回。普通表单通道逐行发布第三对为 +73.11%、第四对为 −23.77%，二者都保留，不选取有利值或通过重跑抹掉失败。

这是相对前版 fork **同样原子模式**的对照，不是相对未修改上游的普遍提速，也不能外推到普通追加或 MySQL/SR/Doris。Apple M5 / 16 GiB、PG 17.11、JDK 8u504、pgJDBC 42.7.13；性能阶段没有同时构建、剖析、压缩或运行其他本地测试，其他项目既有容器仍在运行。

## 两项原型具体做了什么

指纹查询原先在四个聚合表达式中重复计算 SHA-256。`OFFSET 0` 使一层投影供四段求和使用，不改变指纹格式、锁或发布比较。原生 SQL 单次诊断：原查询 2340.055 ms，强制物化 1748.148 ms，OFFSET 方案 1373.363 ms；物化写入 9155 个临时块，OFFSET 为零。这不是 Engine 性能。

12 组三方指纹比较覆盖百万行、空集及特殊字段，每类四次，结果一致；额外用临时纯函数包装和 PG 函数统计计数，64 行原查询调用 256 次、物化和 OFFSET 各 64 次，各四次重复。计数包装检查与原生 SQL 计时分开，包装函数已删除。完整作业收益不稳定，因此这一行改动没有进入生产代码。

逐行发布原型在 PG 17 及以上使用 `MERGE ... ON false ... INSERT ... RETURNING`，逐行比较暂存值与实际写入值的完整 `record_send` 字节，并核对返回行数。只有 INSERT 分支，源重复行保留重数，主键冲突失败；较旧版本保留原有字节分组 SQL，本轮没有旧版本实机验收。PG 官方允许 RETURNING 同时引用源列和写入后的目标列，INSERT 会按目标分区路由，见 [MERGE](https://www.postgresql.org/docs/17/sql-merge.html)。

56 项真实 SQL 检查对照旧分组和新逐行校验，覆盖重复项、NULL、浮点特殊值、numeric/timestamp 精度缩窄、特殊列名、空批次、已有目标行及分区。随后百万行、临时目标表的 EXPLAIN ANALYZE：旧分组 3663.176 ms、新方案 1377.074 ms；根节点累计临时写入由 299647 降到 1342 个 8 KiB 块，约 2.29 GiB → 10.48 MiB。临时目标没有生产 logged 目标的完整 WAL 成本，这些数只解释计划差异，不代替完整作业或峰值磁盘占用。

## 正确性检查与保留的测试

两项原型各通过 45 项单元测试。真实 Engine 检查：

| 原型 | 原子回归结果 / Engine 次数 | 浮点结果 / Engine 次数 | 旧版发布后同 ID 重跑 |
|---|---:|---:|---:|
| 指纹投影 | 125 / 133 | 8 / 16 | 8 对 / 16 次 |
| 逐行发布 | 149 / 157 | 8 / 16 | 8 对 / 16 次 |

包括真实 COMMIT 回执丢失、同 ID 恢复、过期任务隔离、精度缩窄拒绝、脏行/过滤行拒绝等。Engine 次数包含预期失败及每组 8 次旧版首次发布，不能当作成功搬运数或生产错误率统计。

新增的 24 次用例为：JDBC/COPY × 四次重复 × 特殊列名、重复主键、分区路由。生产改动撤回后，用保留下来的 clean `c9b499f` 运行包独立执行这 24 次，全部通过；它们保留在 [postgresql_atomic_checks.py](postgresql_atomic_checks.py)，会继续进入已有 CI。生产 publisher 文件恢复到原有字节分组实现，没有启用 MERGE 或 OFFSET 原型。

## 波动线索、空间与边界

性能结束后提取已有 INFO 日志与 PG checkpoint 日志，没有插入额外计时探针。普通表逐行发布候选第四轮的发布阶段为 10.779 秒，其他候选的第二/三轮约 5.018 / 4.951 秒；基线第三轮发布也达到 13.698 秒。同期 PG 多次提示 WAL checkpoint 过于频繁，部分仅相隔 8–17 秒，`max_wal_size=1024MB`。这是时间重叠和后续诊断线索，尚不能证明是全部波动的原因，原负收益结果不因此作废。

没有修改数据库持久化设置或增大 WAL 配额。复用已有百万行源与容器，逐轮检查 6 GiB 数据预算，两个版本的性能 writer 均通过已验证的 JDBC startup options 设置每后端 `temp_file_limit=1536MB`。归档的全局设置仍显示 `temp_file_limit=-1`，不等于这些 writer 连接没有局部上限；预算检查也不等于整机硬配额。

归档并核验运行包 SHA-256 后，删除两个被否决的运行包，释放 295960816 字节（约 282 MiB），并删除本轮百万行目标。临时根目录 1063664991 字节、PG 数据目录 1474789376 字节；保留百万行源、生产运行包与其他项目容器，无遗留暂存或测试连接。

仍不能据此批准亿级生产回灌：普通追加重试可重复、先前批次可残留；原子模式仅覆盖 PG 单表追加，同 ID 指纹仍为概率校验；源到暂存转换、跨 ID 重叠、其他 writer 和真实业务类型/容量仍需独立验收。
