# PG 原子模式硬崩溃回归与 UNLOGGED 试验

2026-09-27。本轮新增真实数据库进程崩溃、恢复及同 ID 重跑检查，并为 PG 性能脚本记录数据库 WAL 插入位置增量。**UNLOGGED 暂存原型已撤回，生产 publisher 没有变化，默认继续使用 logged 暂存。全场景 +25% / +50% 与亿级零差错仍未验收。**

## 为什么没有保留提速原型

前一轮观察到频繁 WAL checkpoint。本轮只把原子模式的暂存表改为 UNLOGGED，正式目标、批次账本、锁、行数/指纹/完整字节检查和发布事务均保持原实现，没有叠加 MERGE 或指纹投影原型。

UNLOGGED 的数据不写 WAL，崩溃后会被清空，也不复制到备库；这不是可忽略的恢复差异，见 [PostgreSQL CREATE TABLE](https://www.postgresql.org/docs/17/sql-createtable.html)。现有同 ID 自动重跑本来就会重建暂存，但 logged 表还保留了可供人工恢复的原始暂存副本。用户的真实源是否可重新读取尚未确定，因此记录了更严格的决定：**无论速度是否提高，都不直接替换默认 logged 路径**。原型继续测量，只用于判断 WAL 成本，不能当作满足无损要求的正式优化。

三组完整作业也没有通过最初的性能保留条件：各场景中位至少 +5%、每个配对不退步、正确性通过；用户的 +25% / +50% 门槛另行计算。

| 场景 | logged 中位秒 | 原型中位秒 | 中位吞吐变化 | 最差配对 | 每对 +25% / +50% |
|---|---:|---:|---:|---:|---|
| 普通表单通道 | 14.8911 | 14.4884 | +2.78% | −20.35% | 均失败 |
| 生成数据四通道 | 10.2118 | 9.9111 | +3.03% | −6.53% | 均失败 |
| 普通表四通道 | 14.8419 | 13.9691 | +6.25% | +0.68% | 均失败 |

| 场景 | logged 数据库 WAL 中位字节 | 原型中位字节 | 降幅 |
|---|---:|---:|---:|
| 普通表单通道 | 802212200 | 434329888 | 45.86% |
| 生成数据四通道 | 738297704 | 369203728 | 49.99% |
| 普通表四通道 | 814758728 | 447678840 | 45.05% |

WAL 明显减少，但没有转化成相称的墙钟吞吐改善，不能把 WAL 降幅称为速度提升。指标是 Engine 前后数据库 `pg_current_wal_insert_lsn()` 的差值，采样在计时外，包含数据库后台 WAL，不是逐条归属于 DataX 的精确写入量。

## 测量方法

对照为 clean `c9b499f` 的 `candidate-atomic-group-final`；原型为 `286e6ce` 加归档补丁。双方均启用同样的 PG 原子模式和相同并发，源表读取共享快照，COPY/rewrite 均关闭。每场景百万行，每版一次预热、五对 AB/BA，共 36 次完整作业。计时覆盖 JVM、读取、暂存、指纹、二进制比较、账本和发布提交；建表、WAL 采样及外部对账不计时。

36 次均通过数量、全部六列、账本及无遗留暂存检查。生成数据组是百万行相同值，保留其重复数量。样本不是百万条不同业务记录，也不是亿级、在线变化源或所有 writer 的验收。

主机 Apple M5 / 16 GiB，PG 17.11、JDK 8u504、pgJDBC 42.7.13。没有并行运行构建、JFR、压缩、其他 Engine 或数据库测试；做过轻量离线 YAML/源码语法检查及文件读写，其他项目容器仍运行。因此计划中“不运行其他本地测试”的表述并非绝对满足，隔离差异单独归档，没有剔除或重跑慢轮来改善分数。

这仍是相对前版 fork **同一原子模式**的比较，不是相对未修改上游或其他数据库的提速证明。

## 真实崩溃与严格恢复校验

新增 [postgresql_atomic_crash_checks.py](postgresql_atomic_crash_checks.py)，只针对专用 `datax-perf-postgres` 容器。用 `docker kill --signal=KILL` 杀停，再启动同一容器；每次验证 postmaster 启动时间改变。归档包含 PG 自动恢复日志。没有重启 Docker 服务或其他项目容器。

| 崩溃位置 | 如何达到该位置 | 恢复后必须成立 |
|---|---|---|
| 暂存全部写完、发布前 | 测试连接持有目标表锁，等待 publisher 阻塞 | 原有目标行不变；未发布数据和账本不存在 |
| 发布事务执行中 | 测试 CHECK 函数在特定记录上等待 advisory lock，非事务序列证明已处理多行 | 未提交的正式数据回滚；原有行不变；无账本 |
| 已提交、客户端未收到回执 | 现有 TCP 代理截断最终 COMMIT 回执，Engine 必须报告提交不确定 | 正式行和账本均持久存在；已删除暂存不会复活 |

修正后的正式检查为：logged 对照与 UNLOGGED 原型各 24 个场景，即三种位置 × JDBC/COPY × 四次重复，共 48 次进程硬崩溃、144 次 Engine（每场景中断、恢复、再次重跑）。源有 8 行，包含重复项、NULL、整数/小数边界、时间及二进制字段；目标事先另存一条旧记录。

每次对源、原有目标行以及新写入的完整二进制行做精确比较，保留重复数量；显式断言未发布时目标为 1 行、发布后为 9 行，账本分别为 0/1 条。两次同 ID 重跑均记录为精确 9 行，无重复或残留暂存。logged 暂存在前两类崩溃后保留 8 行，UNLOGGED 清空为 0 行，实测确认了恢复副本的差异。

初版验证器使用 `id<>0` 排除旧记录，会遗漏额外 NULL 键行，而且读取总数后没有断言。审查发现后改用 `IS DISTINCT FROM`、断言总数，并加入负向检查：故意额外写入一条 NULL 键行，验证器必须拒绝。还把两次恢复的明细写入结果。两版都完整重跑了上述 48 个场景，负向检查通过；初版另外 48 个场景和较弱的原始结果完整保留，**不计作修正后的严格通过证据**。

这些是单实例 PG 进程级崩溃，不是整机断电、磁盘损坏、跨机故障转移或持续变化源的验证。源保持不变是本夹具的明确条件，不能因此承诺任意生产回灌零错误率。

## 其他回归与保留下来的改动

原型另通过 45 项单元测试，原子回归 149 条结果 / 157 次 Engine，浮点 8 条 / 16 次 Engine，旧版发布后新版同 ID 重跑 8 对 / 16 次 Engine。这些包括预期失败，不能当作成功作业数或生产错误率统计。

生产 Java 源已恢复，与试验前完全一致。保留新的硬崩溃检查及 WAL 计量；已有 data-fidelity 工作流增加独立的 `postgres-crash-recovery` job，在自己的 PG 容器验证 **logged** 模式，避免重启主回归 job 使用的数据库。其检查结果和未完成项会输出到 CI 日志。

保留的运行包 `c9b499f` 已通过修正后的 24 个 logged 场景；不需要把被否决的原型当作正式运行包。上一提交 `286e6ce` 的 [MySQL CI](https://github.com/dangzitou/DataX/actions/runs/36291790054)和 [PG/SR/Doris CI](https://github.com/dangzitou/DataX/actions/runs/36291790045)均成功，但不替代本次新增 CI job 的独立终态。

```sh
  --scenario table-single --atomic --rounds 5
```

沿用百万行源与现有容器，没有新建大源表或放大 WAL 配额；正式目标和账本的持久化设置未降低。性能连接仍使用每后端 `temp_file_limit=1536MB`，逐轮检查 6 GiB 预算，两者都不是整机硬配额。
