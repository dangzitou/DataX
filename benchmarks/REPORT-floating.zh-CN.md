# 浮点保真、过滤错误与 PostgreSQL 驱动升级

2026-09-27。修复公共浮点转换对特殊值和负零的错误处理，并升级 PG reader/writer 的
JDBC 驱动以读取二进制 NUMERIC 无穷值。**全场景 +25% / +50% 和亿级零差错仍未验收。**

## 重复复现与修复

未修改上游 `80ec23d` 和前版 fork `6c77ab5` 各在四个独立 JVM 中执行相同探针。
每次 11 个断言中，5 个特殊值被错误拒绝，4 个负零变成正零，2 个普通值/极小值对照通过。
这些是直接公共 API 检查，不是数据库迁移。

- `DoubleColumn` 构造接受 `Infinity` 和大小写变体，`asDouble()` 却不能处理全部已接受形式；
  `+Infinity` 的转换分支也因构造校验拒绝而不可达。现在统一这些特殊值的处理。
- Double/Float 构造先经过 BigDecimal，导致负零符号消失且 NaN/Infinity 抛异常；
  对这些 IEEE 特殊值保留原始字符串，其他有限值保持原来的十进制文本格式。
- DoubleColumn 和 StringColumn 的 `asDouble()` 在十进制值为零时保留原始负号。
  既有数值越界检查继续生效，没有放宽十进制向有限 double 的范围限制。

公共修复为 `3fccc88`，驱动升级为 `973d440`。两份独立、干净构建分别使用
pgJDBC 42.3.3 / 42.7.13；所有 JAR 哈希都记录并核对。PG 读写插件使用相同驱动版本。
使用已有驱动的修复，没有自行实现 PG 二进制 NUMERIC 解析。
官方在 [42.7.4 变更记录](https://jdbc.postgresql.org/changelogs/2024-08-22-42/)记录了
NUMERIC Infinity 支持；本次采用[官方 Java 8 版本 42.7.13](https://jdbc.postgresql.org/download/)。
该版本不保证兼容 PG 9.1 以前的服务端；本轮实际服务器为 PG 17.11，不能把驱动声明的
兼容范围当作已完成的 DataX 各版本回归。

## 真实 PG 与回归

本机 PostgreSQL 17.11，JDK 8u504，fsync/synchronous_commit/full_page_writes 开启。
14 行夹具没有目标主键，包含有意重复行、NULL、正负零、正负无穷、NaN、浮点最大值、
最小非零值、相邻于 1 的浮点值及高精度 numeric。使用 float4send/float8send 的十六进制
和 numeric 文本做双向 EXCEPT ALL；普通数值相等判断会把正负零视为相等，不能代替此检查。

过滤场景配置 `< -Infinity`，按 IEEE 比较语义不应过滤任何输入。旧版文本模式却在转换
正无穷时出错，每次只留下 13 行并报告失败；直接文本传输的对照保持 14 行完全一致。
请求二进制模式时，42.3.3 还会在解码 NUMERIC Infinity 时抛 invalid sign 异常。

| 版本 | 结果条目 | 精确往返 | 按复现要求失败 |
|---|---:|---:|---:|
| 未修改上游，仅 JDBC | 16 | 4 | 12 |
| 前版 fork，JDBC/COPY | 32 | 8 | 24 |
| 仅公共修复，仍为旧驱动 | 32 | 16 | 16 |
| 公共修复 + 新驱动 | 32 | 32 | 0 |

每个组合重复四次。以上均为完整 Engine 作业；失败可以留下已提交行，不表示整作业回滚。
补充原子发布：JDBC/COPY、请求二进制及过滤路径各四次，8 个结果对应 16 次 Engine；
首次发布和同 ID 重跑分别验证，均为原样 14 行，没有额外追加。它仍只覆盖实验性 PG 单表模式。

66 项 JUnit 通过，其中新增五项覆盖特殊值、符号、原有精度/格式、范围拒绝和固定种子的
4096 组 double/float 位模式。NaN 按规范化值检查，没有声称保留任意 NaN payload 位。
既有 PG 类型、时间、整数绑定、COPY、分片、共享快照、原子发布、提交回执故障和文件检查
也重新运行。本轮回归与候选浮点检查共 331 个结果条目，另有 8 项真实 JDBC 整数读取检查；
包含原版对照、历史风险复现、直接 API 检查、预期失败及一条结果对应多个 Engine 的情况，
不能把结果总数称作安全迁移次数。

初次单测有一个旧格式预期写错（`0.00000010` 被误写为 `0.0000001`），已修正测试而保持
旧格式；初次真实检查另发现二进制 NUMERIC 兼容问题，随后独立复现并修复。失败日志均保留。

## 性能与边界

每组一百万行、双方各一次预热和五对 AB/BA，计完整 JVM 耗时，排除建表、验证。
同组并发、fetchSize=1024、batchSize=1024、1 GiB JVM、UTC 配置一致，未开启 rewrite/COPY。
普通表场景分别单通道、四通道，生成数据写入和导出文件使用各自固定配置。
候选为 clean `973d440`，前版为 `6c77ab5`，上游为未修改 `80ec23d`。
驱动隔离对照为 `3fccc88` 对 `973d440`：公共修复一致，只升级 PG 依赖；打包发生变化的
项目 JAR 内 class 也逐个核对相同。驱动的 checker-qual 传递依赖同步更新。

以下是基线耗时中位数 / 候选耗时中位数 − 1 的吞吐变化，不是逐对收益的中位数。

| 场景 | 相对前版 fork | 相对未修改上游 | 仅升级 PG 依赖 |
|---|---:|---:|---:|
| 普通 PG 表，单通道 | +1.94% | +7.26% | +2.81% |
| 普通 PG 表，四通道 | +3.22% | +4.24% | NOT_RUN |
| 生成数据写 PG | +5.94% | −3.58%；独立复测 +6.93% | −3.90% |
| PG 导出文件 | +3.08% | +8.33% | +0.08% |

最初十组计划在计时前保存。观察到生成数据写入相对上游 −3.58% 后，提前记录仅追加
上游复测和驱动隔离这两组；没有不断重跑直到得到喜欢的结果。两次上游结果方向不同，
驱动隔离组也出现中位变化为负而四个配对为正，说明小收益/回退存在明显波动。
两次结果全部保留，不能声称已确认稳定提速，也不能简单删除负值。

十二组共 **144 次百万行作业**，预热也验证数据；数据库检查核对每个字段及行数，
有序文件逐字节匹配原生参考。**十二组逐轮 +25% / +50% 均失败**。
这是重复百万行测试，不是一次亿级作业。Apple M5 / 16 GiB、PG 4 CPU / 2 GiB；
其他项目既有容器继续运行，不是独占主机。计时期间没有本地构建、采样、压缩或其他测试。
首次汇总曾误用 gate 函数的位置参数；改用命名参数并核对每组原始 gate.json 后修正，
无效汇总明确另存为 invalid-arguments，不用于本报告，原始运行数据没有修改。

这些改动不提供通用幂等、整作业回滚或亿级容量保证。公共转换的其他数据库调用方没有全部
实测；目标不支持特殊浮点值时仍可能明确失败。跨类型缩窄、所有数据库版本和生产错误率
均未验收；本次字段检查针对上述夹具与相同类型的 PG 目标。

## 复现、证据与空间

按[构建指南](README.md)准备 JDK 8 与运行包，只使用专用测试容器和 datax_bench 数据库：

```sh
python3 benchmarks/postgresql_float_checks.py /tmp/datax-baseline /tmp/float-before --jdbc-only --expect-filter-failure --expect-binary-numeric-failure
python3 benchmarks/postgresql_float_checks.py /tmp/datax-candidate /tmp/float-after
python3 benchmarks/postgresql_float_checks.py /tmp/datax-candidate /tmp/float-atomic --atomic
```

性能脚本、各次配置/日志、完整结果、两个计划、构建元数据和文件哈希位于
[本轮证据目录](results/2026-09-27-floating/)。源夹具没有业务数据，数据库和 HTTP 故障检查
也不能代表生产环境全覆盖。已把浮点往返和原子重跑接入远端 CI。

复用已有百万行源，未新建容器。每轮文件校验后删除输出，组结束删除参考文件，沿用
6 GiB 数据预算与 1 GiB 余量的轮次间检查，它不是硬配额。
归档并核验 JAR 后删除中间对照运行包，释放约 140 MiB；清理本轮目标表及浮点夹具后，
PG 数据目录约 1.37 GiB，临时根目录约 1.02 GiB，本轮归档约 2.8 MiB。
保留未修改上游、前版与最终候选运行包；没有清理其他项目的容器或数据。
