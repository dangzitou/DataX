# PG 原子发布：保留完整字节校验的性能改进

2026-09-27，生产提交 `c9b499f`。减少原子发布时的重复读取和编码，两组百万行完整作业相对前版原子模式分别提高 **6.14% / 13.16%** 中位吞吐。**全场景最低 +25%、目标 +50% 和亿级零差错均未验收。**

## 生产变化与正确性

此前发布 SQL 对暂存与 INSERT RETURNING 结果分别编码，再做两个方向的 EXCEPT ALL。现在直接返回写入行的 `record_send` 字节，将暂存行计为 +1、写入行计为 −1，按完整 bytea 分组核对计数和。任意组非零即失败并回滚。NULL、字段类型、精度、负零和重复行数量仍参与完整字节比较，账本的 SHA-256 指纹格式没有改变。

这是 PG 原生分组与整数聚合；没有新增依赖。集合重数与聚合语义见 [集合运算](https://www.postgresql.org/docs/17/queries-union.html)和 [聚合函数](https://www.postgresql.org/docs/17/functions-aggregate.html)。正式插入、对账、批次登记与删除暂存仍在同一事务；锁、旧任务隔离、脏行拒绝和自定义类型拒绝均保持原实现。

真实 PG 17.11、JDK 8u504、pgJDBC 42.7.13 的检查包括：

- 45 项单元测试通过；36 项直接 SQL 检查分别验证空集合、顺序变化、缺少/多出重复项、相同总数但不同重数、字节变化、NULL/空值、负零及 numeric 显示精度，与原双向 EXCEPT ALL 的判定一致。
- 原子模式 125 条结果、133 次 Engine 检查通过，包括精度拒绝、同 ID 重跑、约束失败、过滤/脏行、真实 COMMIT 回执丢失和旧任务恢复隔离。
- 浮点 8 条结果、16 次 Engine 检查通过，包含 JDBC/COPY、二进制读取、特殊值、首次发布与重跑。
- 旧版发布后新版同 ID 重跑，JDBC/COPY 各四组，共 16 次 Engine；目标仍为精确 8 行、账本一条、无暂存。证明这些夹具的旧批次登记可继续识别。

以上 Engine 合计 165 次，包含 8 次旧运行包发布及许多预期失败；不是 165 次成功搬运，也不是生产错误率统计。

## 完整作业性能

对照双方均启用相同 PG 原子模式，均关闭默认未开启的 JDBC 批量合并。PG 源使用共享快照。每组一百万行，双方各一次预热，五对 AB/BA；计时包括 JVM、读取、暂存、指纹、完整字节核对与发布提交。每次作业后另核对行数、全部六列、账本行数及无遗留暂存。建表与外部校验不计入耗时。

| 场景 | 前版中位秒 | 新版中位秒 | 吞吐变化 | 最差配对 | 每对 +25% / +50% |
|---|---:|---:|---:|---:|---|
| 普通 PG 表，单通道 | 17.0668 | 16.0792 | +6.14% | +2.29% | 均失败 |
| 生成数据写 PG，四通道 | 12.1604 | 10.7458 | +13.16% | +9.89% | 均失败 |

24 次百万行作业均通过数据检查，所有配对为正；符合试验前记录的保留条件：两组中位至少 +5%、无负收益配对且正确性通过。这个保留条件不替代用户的最终门槛。普通表第三对收益为 +39.61%，其余配对较小，完整数据保留，不挑选该异常高值作整体结论。

基线为 clean `5f0c22b`，候选最初为 `9d24e0f` 加归档补丁。通过验证后提交为 `c9b499f` 并重新干净构建；所有 JAR 的实际条目内容与试验包完全一致，只有一个 JAR 的 ZIP 打包字节变化，类、资源、manifest 和服务注册内容都核对一致。

这是相对前版 fork 的**同一原子模式**对照，不是相对未修改上游的提速，更不能外推到 MySQL/SR/Doris 或普通非原子路径。主机为 Apple M5 / 16 GiB，其他项目既有容器仍在运行；计时期间未同时构建、剖析、压缩或运行其他本地测试。

## 被否决的批量合并与空间限制纠正

此前普通写入的原生 JDBC rewrite 试验不能代表原子模式。本轮又对同一旧运行包做原子模式开/关对照：各一百万行、一次预热和五对，24 次作业全部验证。

| 场景 | 关闭→开启的中位秒 | 中位吞吐变化 | 最差配对 |
|---|---:|---:|---:|
| 普通 PG 表 | 15.2516 → 14.0717 | +8.38% | +7.77% |
| 生成数据写 PG | 11.6021 → 11.3170 | +2.52% | −0.88% |

两组 +25% / +50% 均失败，第二组还未满足预先约定的保留条件，因此没有改变普通模式或原子模式的 rewrite 默认值。

初次试验错误地通过 `session` 设置 PG 临时空间上限。代码检查发现 PG 没有执行该配置，主动停止该组、保留已验证和未验证记录，并清理被中止作业的自有暂存。之后改为双方相同的 JDBC startup `options`，用两次真实 JDBC `SHOW temp_file_limit` 确认 1536MB 生效，再完整重跑。初次中止组不计入上述 48 次完整性能作业。

基准工具新增 `--atomic`，检查双方都实际写入批次账本，并在每次作业开始前记录 `pending_run`。尚未完成数据验证的作业不能被性能门槛接受。

## 执行计划与仍需解决的问题

三次单独的原生 SQL EXPLAIN ANALYZE 诊断不计入 Engine 基准。旧比较、新分组和强制排序分组耗时分别为 5.271 / 4.486 / 3.808 秒；单次诊断不能作为稳定性能收益。

新分组计划出现 165 个 HashAgg 批次，报告落盘约 754 MiB；顶层累计临时写入为 299647 个 8 KiB 块，旧 SQL 为 129754 块。**本次较快的完整作业伴随该诊断中更多的临时 I/O**，没有宣称空间和 I/O 都下降。强制排序只做了诊断，没有加入生产代码，需要完整对照与故障回归后才能考虑。

复用已有百万行源，没有新建容器。保留逐轮 6 GiB 数据预算检查，原子基准另通过数据库连接设置每后端 1536MB 临时文件上限；两者都不是整台机器或亿级作业的空间保证。暂存、WAL、索引、发布锁及业务对账的容量和耗时仍需按实际目标验收。
