# 第二轮：querySql 性能逐轮验收

> 历史实验记录：本轮应用层语句缓存随后因对照回退被删除；本报告数字不代表当前代码。当前交付版本见[最终报告](REPORT-final.zh-CN.md)。

2026-09-26，代码版本 [`34096bf`](https://github.com/dangzitou/DataX/commit/34096bf1ceb06b724ab66d0256363d6a714d089d)，
原版基线 [`80ec23d`](https://github.com/alibaba/DataX/commit/80ec23d5c5328eb90ca364d2749e92dfaf44541e)。

**100 万行 MySQL → DataX → MySQL，单条 querySql 开启自动四路并行：七轮吞吐提升均超过 50%，最低 55.48%，中位数提升 73.76%；每轮逐字段比对，数据差异为零。**

这满足本次固定负载的逐轮验收。**未证明所有任务都能提升 50%**：不开启分片、原版已手工并行的对照仍未达标，结果完整保留在下面。吞吐提升 50% 与耗时减少 50% 不同；本次主实验耗时中位数减少 42.45%，没有达到耗时减半。

## 为什么继续修改

[第一轮报告](REPORT.zh-CN.md) 的中位数提升为 50.79%，但最慢一对只有 28.17%，不符合逐轮至少提升 50% 的要求。第二轮没有删除第一轮证据。

对完整 DataX 进程做 JFR 采样，并检查 MySQL performance_schema，发现读取线程经常等待写入端。写入端反复创建 PreparedStatement，每批重复设置 autocommit。第二轮在公共 JDBC writer 中复用每个任务的语句，只在需要时改变 autocommit；提交频率仍按原配置逐批执行。批量失败时关闭旧语句，再回滚并进入原有逐行处理，下一批重新创建语句；正常结束和元数据获取失败均关闭资源。

新增性能门禁要求每一对测量都达标；任意一轮不足、校验失败或证据不完整均非零退出。第一轮数据在此门禁下失败，第二轮主实验通过。门禁接受的是已测样本，不能预测未来每次运行或未知生产负载。

## 同一环境、完整链路

- Apple M5，10 CPU，16 GiB，macOS 27；隔离 MySQL 8.0.46 容器限制 6 CPU / 4 GiB，buffer pool 1 GiB。主机与数据库共享硬件，没有绑核或控制频率。
- 两版均使用 Zulu 8u504、Connector/J 5.1.47、1 GiB JVM 堆；channel 上限 4、writer batchSize 1024、相同 SQL 和字段。原版单条 querySql 实际产生一个任务，新功能产生四个任务。
- 100 万行，6 列：整数、DECIMAL、DATETIME、中文、NULL、256 字节 payload；是生成数据，实际通过 MySQL 协议读写真实表，并非 mock 或内存微测试。
- 数据库 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`，没有降低持久化要求。源表在实验期间保持静止。
- 每组先各预热一次，再 AB/BA 交替。计时从 JVM 进程启动到成功退出，包括初始化、自动范围发现、读取、转换、通道和写入；建表/造数和事后全字段校验不计入。两版完成轮询间隔相同，均为 200ms。
- 每轮重建目标表，校验行数、主键唯一性以及每个字段的 NULL 安全相等。三组正式实验共 40 次百万行同步（包含各组预热），差异均为零。采样诊断与试跑不混入正式统计。

## 主实验七轮结果

| 轮次 | 原版耗时 | 新版耗时 | 吞吐提升 | 差异行数 |
|---|---:|---:|---:|---:|
| 1 | 13.071s | 7.169s | 82.32% | 0 |
| 2 | 13.702s | 7.514s | 82.36% | 0 |
| 3 | 12.948s | 7.500s | 72.64% | 0 |
| 4 | 13.913s | 7.145s | 94.71% | 0 |
| 5 | 13.033s | 8.382s | 55.48% | 0 |
| 6 | 12.952s | 8.172s | 58.49% | 0 |
| 7 | 12.672s | 7.128s | 77.79% | 0 |

中位耗时 **13.033s → 7.500s**；吞吐提升按 `baseline / candidate - 1` 计算，为 **73.76%**。按 `1 - candidate / baseline` 计算的耗时减少为 **42.45%**。DataX 进程峰值 RSS 中位数 **450.50 → 471.66 MiB**，并行会消耗更多内存。

## 对照结果也保留

| 场景 | 测量轮数 | 原版中位耗时 | 新版中位耗时 | 吞吐变化 | 每轮至少 +50% |
|---|---:|---:|---:|---:|---|
| 单条 querySql → 自动四路并行 | 7 | 13.033s | 7.500s | +73.76% | 通过 |
| 均不开分片，实际各一条任务 | 5 | 13.507s | 14.770s | **-8.55%** | 未通过 |
| 原版手工四路 → 自动四路 | 5 | 8.659s | 8.990s | **-3.68%** | 未通过 |

各组单独预热和测量，不能跨组挑选基线或最快耗时来计算提升。关闭分片的对照出现了回退，手工并行对照也没有额外 50% 收益。因此，不能用主实验通过宣称整个 DataX 或任意配置都通过了 50% 性能要求。

为调查回退，又用第一轮的 `456a29b` 作为基线，分别对比本轮 writer 改动和删除语句缓存后的最小改法，各四轮、均为单线程。保留缓存的版本中位数变化为 **-3.92%**，每轮 -15.63%～+23.17%；只保留 autocommit 判断和资源清理的版本为 **+0.55%**，每轮 -3.01%～+4.19%。这些小样本不足以证明普遍加速，但没有给语句缓存提供稳定收益的证据，因此最终代码删除了缓存，另行验收，不能沿用本报告的七轮成绩。

删除缓存后的 `417623d` 又完整测了七轮：中位数提升 58.56%，但第 2、7 轮只有 42.06%、46.61%，严格门禁失败。[全部结果及失败门禁](results/2026-09-26-guard/gate.json)保留在仓库；最终版本改用驱动原生缓存，并重新做了整组测试，没有沿用本轮成绩。

诊断采样中，autocommit 设置次数从 984 次减至 8 次，INSERT 和 COMMIT 均保持 977 次。该结果证明消除了重复设置、保留逐批提交，不代表整个任务提升了相同比例。JFR 只用于定位，没有将带采样的进程耗时加入正式结果。

## 正确性与持续检查

- 26 项 Java 单元测试通过，包括新增的逐批提交/语句复用、失败批次恢复、元数据失败后资源关闭。
- 32 项真实 MySQL 检查通过，包含原有边界 SQL、NULL、unsigned BIGINT、SQL 错误、超时、连接终止，以及四次新增的“中间批次主键冲突 → 回滚 → 逐行处理 → 后续批次恢复”。
- [GitHub CI](https://github.com/dangzitou/DataX/actions/runs/36237290147) 在 Linux / Temurin 8 上通过上述单测和真实数据库检查，并检查性能门禁逻辑。CI 功能数据量为 10,000 行，不把共享 CI 机器的耗时当作性能证明。

## 复现与使用边界

完整环境、构建与配置见 [README](README.md)。主实验与门禁命令：

```sh
python3 benchmarks/mysql_querysql.py /tmp/datax-benchmark/baseline \
  /tmp/datax-benchmark/candidate /tmp/datax-benchmark/parallel \
  --seed --rows 1000000 --rounds 7 --channels 4
python3 benchmarks/performance_gate.py /tmp/datax-benchmark/parallel/results.json \
  --metric throughput --threshold 50 --minimum-rounds 7
```

业务任务需要在 `mysqlreader.parameter` 设置 `"querySqlSplitPk": "id"`，输出列需为整数类型，配合 `job.setting.speed.channel=4`；具体列名和并发数必须适合业务表。并行查询不共享事务快照，要求数据源静止、SQL 确定；不保留跨任务排序。数据倾斜、没有可用索引、物化子查询、目标库饱和或限速都会改变结果。

本次没有验证未知生产 SQL、其他数据库、多小时压力测试、所有可选插件或未来运行的性能下限。实际业务的“至少 50%”必须固定任务配置、数据分布、数据库版本、硬件和指标后重新验收。
