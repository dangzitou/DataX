# PG 单次发布原型：完整测试后撤回

2026-09-27。**该原型未保留：虽然普通表单路/四路中位吞吐提高 28.09% / 30.71%，重复数据写入场景下降 22.74%。生产发布实现恢复为 `f9a7612`；全场景 +25% / +50% 未达到，也没有亿级零差错证明。**

## 对照与实现范围

对照为 `candidate-calendar-final`，生产实现对应 `f9a7612`，包括日期时间有损转换检测。候选为同一提交加归档的 `atomic-singlepass-prototype.patch`。双方均启用 PG 原子追加、普通 logged 暂存及目标，COPY 和 JDBC rewrite 关闭；数据库持久化设置保持启用。

候选在 PG 17 首次发布时，将 `MERGE ... RETURNING` 的逐行源/目标二进制比较和原有四段 SHA-256 数值累加指纹放入一个修改数据的 CTE。它试图减少独立扫描；仍检查完整二进制值与行数，不以哈希代替首次发布的精确比较。同批次重跑沿用原指纹格式，保留锁、代际检查和同事务登记。旧 PG 分支仍用原路径，但本轮没有旧 PG 服务端实测。

这是相对前一版 fork 的实验，不是相对未修改上游的全场景提速。完整补丁仅作为实验记录归档，未进入生产 Java 文件。

## 预先确定的门槛与实际结果

计划在运行前写入 `atomic-singlepass-plan.json`：正确性、升级和崩溃检查通过，并且三个场景各自中位吞吐至少 +5%、每个配对不回退，才保留原型。用户的每对 +25% / +50% 目标另外评估，不能用较低的原型保留门槛代替。

每场景百万行、双方各一次预热及五对 AB/BA，共 36 次完整 Engine；并发数在每对内相同。计时覆盖整个 JVM 作业，建表、重置和外部对账在计时外。使用全部预定轮次，未删除慢轮。

| 场景 | 对照中位秒 | 候选中位秒 | 中位吞吐变化 | 最差配对 | 每对 +25% | 每对 +50% |
|---|---:|---:|---:|---:|---|---|
| 普通表单通道 | 15.1245 | 11.8073 | +28.09% | +21.01% | 失败 | 失败 |
| streamreader 重复数据、四通道 | 10.0301 | 12.9817 | −22.74% | −23.58% | 失败 | 失败 |
| 普通表四通道 | 14.4748 | 11.0740 | +30.71% | +27.52% | 通过 | 失败 |

全部作业均核对百万行、六列字段、批次登记行数及暂存清理。普通表以主键对应全字段，重复数据场景逐行核对常量值及重复数量。**数据正确性检查通过，不意味着性能门槛通过。** 重复数据场景五对变化分别为 −21.91%、+43.66%、−23.58%、+45.13%、−22.74%；保留波动，不把回退归因于尚未证实的原因。

主机 Apple M5 / 16 GiB，PG 17.11，JDK 8u504，pgJDBC 42.7.13。计时期间没有并行构建、数据库测试、压缩或其他 DataX Engine；其他项目容器仍运行。结果只适用于这些本地静态夹具。

## 正确性证据

| 检查 | 结果条目 | Engine 次数 | 结果 |
|---|---:|---:|---|
| 原子发布回归 | 149 | 157 | 包括预期拒绝在内，断言通过 |
| 发布前、发布中、发布后硬崩溃 | 24 | 72 | 精确检查和同 ID 恢复通过 |
| 日期时间保真与有损转换拒绝 | 64 | 80 | 16 项必须失败；其余精确对账通过 |
| 原子浮点保真及重跑 | 8 | 16 | 二进制值与重复次数一致 |
| 旧→新、新→旧同 ID 兼容 | 16 | 32 | JDBC/COPY 各四次；8 行、1 个登记、0 暂存 |
| 三个百万行性能场景 | 36 | 36 | 全字段和行数对账通过 |

另有 24 次原生 SQL 检查，比较原指纹与候选指纹，并确认目标精度缩窄被识别；覆盖重复、NULL、特殊值、空数据、特殊标识符和分区表。其 TEMP 目标的执行计划仅为诊断，不计入 Engine 性能结论。common/core/RDBMS 单元检查共 53 项通过。

这些是特定测试的通过数，不能换算成生产错误率。尤其不能从“暂存与目标一致”推导“源与目标一致”：reader 先前的日期转换问题已经证明两者不同，见[日期时间安全报告](REPORT-pg-calendar.zh-CN.md)。

## 复现、撤回和容量边界

[证据目录](results/2026-09-27-atomic-singlepass/)包含预先记录的计划、原型补丁、运行/汇总脚本、所有配置和日志、构建元数据、完整结果与 SHA-256 清单。归档时重新验证双方运行包的所有 JAR 哈希。`run-atomic-singlepass.py` 记录本轮调用顺序；各性能组可用：

```sh
python3 benchmarks/postgresql_scenarios.py /tmp/previous /tmp/prototype /tmp/results \
  --scenario table-parallel --rounds 5 --atomic
```

夹具只用于专用 `datax-perf-postgres` 容器，最多百万行，含临时文件限制及磁盘余量检查。归档后删除被拒绝的候选运行包和百万行目标，保留原源表和生产运行包；实际清理量与余量记录于 `storage.json`。

普通追加的部分提交和重跑重复风险仍存在。PG 原子模式只保护符合约束、内容固定、同 ID 的单表批次；不同 ID 范围重叠、重跑时源变化、reader 未报告的漏读/改值、账本或目标被外部修改均不能被泛化保证。其他 writer 不继承 PG 的原子语义。亿级真实 schema、完整源目标对账、容量及跨机故障验证尚未完成，不能把本轮结果当作生产投用验收。
